# 13. Один воркер сервера串行ирует все модели

(ERRORS.md #5, аудит 2026-11-23.) npu_server: один поток обрабатывает все запросы кроме LOAD; зависший движок живёт до RUN_TIMEOUT_S (300 с), все остальные (RUN по здоровой модели, LIST/OPS) ждут.
**Исправление.** 2e81d29: каждый RUN/OPS/GRAPH — свой поток (пер-модельная сериализация e->mu, ответы под wmu), как уже было у LOAD.
**Запись истории:** Закрыта (локально), 2026-11-24. Проверка: компиляция, порядок блокировок по исходникам. Без аппаратного теста.

**Сверка всех карточек, 2026-11-24, f86b309.** Обычные RUN/OPS вынесены в потоки, но UNLOAD остаётся в общем worker. В хостовом тесте собраны исходные worker, handle и engine_remove без кода выполнения LiteRT. При удерживаемом мьютексе модели (состояние выполняющегося RUN) поставлены в очередь UNLOAD этой модели и LIST. За 250 мс ответа не было; обработка возобновилась после освобождения мьютекса. Выгрузку, ожидающую конкретную модель, вынести из общего воркера. Приёмка: LIST и запрос другой модели получают ответы, пока выгрузка всё ещё ждёт RUN.

**Итоговая приёмка, 2026-11-24.** NPU_UNLOAD вынесен из общего воркера в свой поток на запрос (рядом с RUN/OPS/GRAPH): он ждёт мьютекс модели без блокировки остальных. Поведенческий стенд с фейковым движком (настоящие worker/handle/engine_* извлечены из npu_server.cc, процесс-движок — заглушка на том же протоколе): при удерживаемом 1,5 с «RUN» модели 2 в полёте UNLOAD модели 2 — LIST здоровой модели 3 ответил за 50 мс, RUN модели 3 ответил сразу; UNLOAD завершился после RUN и ответил своим тегом.
