# 1. Медленный клиент задерживает ответы всем пользователям NPU

**Где и почему.** В `npu-open/host/npu_daemon.cc` единственный поток `usb_loop` передаёт ответ в `Client::send`. Синхронная запись в клиентский сокет может ждать неограниченно. Локальная проверка подтвердила блокировку записи. Из кода следует, что в это время демон не разбирает ответы для остальных клиентов.

**Что изменить.** Ограничить время доставки одного полного ответа монотонным дедлайном. Учитывать частичные записи и прерывания. По истечении срока пометить соединение закрытым и разбудить его читающий поток через `shutdown`. Оставить единственный `close` владельцу дескриптора в `client_loop`. Сохранить сериализацию заголовка и тела и существующий учёт выполняющихся запросов.

**Приёмка.** На локальных сокетах проверить, что остановившийся получатель отключается за ограниченное время, следующий исправный получатель принимает полный ответ с исходным тегом, а поздний ответ закрытому клиенту отбрасывается. На плате подтвердить, что второе приложение продолжает работу без перезапуска демона.

**Запись истории:** Исправлено локально, ожидает платы. 2026-11-24, коммит 257f643. `Client::send` работает под монотонным дедлайном (REPLY_DELIVER_TIMEOUT_MS): poll(POLLOUT) перед каждой записью, частичные записи и EINTR сохранены, по дедлайну/ошибке — `gone` и `shutdown`, будящий поток `client_loop`; единственный `close` остаётся у владельца. Сборка aarch64 прошла. Приёмка с остановившимся получателем требует ответа больше сокетного буфера — на плате.

**Повторная проверка 2026-11-24, ac2e53b. Открыта повторно.** Сокет от accept4 блокирующий. POLLOUT гарантирует возможность начать запись, но send без MSG_DONTWAIT может ждать на большом ответе дольше дедлайна. Вычитать now из deadline только после проверки now >= deadline, при ошибке выходить из обоих циклов. Приёмка на socketpair с ответом больше буфера и проверкой следующего клиента.

## Порядок исправления и проверка результата

Начать с Client::send в npu-open/host/npu_daemon.cc. Принимать сокет в прежнем режиме для client_loop, а для каждой записи заголовка и тела применять MSG_DONTWAIT вместе с MSG_NOSIGNAL. После короткой записи сдвинуть указатель на фактически переданные байты. После EINTR или EAGAIN заново вычислить остаток общего монотонного срока. По истечении срока под wmu выставить gone, вызвать shutdown и выйти из функции. Дескриптор закрывает client_loop.

Проверка на локальных сокетах. Первый клиент читает частями и получает точные заголовок, тег и тело. Второй перестаёт читать ответ больше его сокетного буфера. После дедлайна отправитель возвращается, поздний ответ отбрасывается, исправный клиент получает следующий ответ целиком. Поставить внешний тайм-аут теста больше дедлайна. Блокирующий путь в ac2e53b установлен по коду.

**Запись истории:** На проверке. 2026-11-24, коммит 62a85fa. `Client` перенесён в заголовок `npu_daemon_client.h` (тестируется на plain socketpair): каждая запись — `send(MSG_DONTWAIT | MSG_NOSIGNAL)`, частичные записи сдвигают указатель, EINTR повторяется, на EAGAIN — poll на остаток общего монотонного дедлайна (остаток вычисляется после проверки `now >= deadline`), по дедлайну/ошибке — `gone` и `shutdown` (единственный `close` остаётся в `client_loop`), дедлайн переопределяется `NPU_DAEMON_DELIVER_TIMEOUT_US` (по умолчанию 10 с). Локальная приёмка: ответ 300 КБ по буферу 64 КБ — исправный клиент получает ответ целиком с исходным тегом, остановленный клиент отключается за ~800 мс и его читающая сторона пробуждена, поздний ответ отбрасывается, следующий клиент не затронут (тест зелёный).
